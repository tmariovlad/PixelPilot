## U1: streamed capture vs quiet, uplink ON, no relaunch (~17 min)

Question (H1 of uplink-t4-analysis): does a streaming `adb logcat` over Wi-Fi cost the RTL video packets?

- Air: one `m7b25f46` 17 dBm step of **≥ 1020 s**, started just before the Quest command.
- Quest (the prefs as installed, rx-diag off, uplink ON):
  `bash stream_ab.sh u1 120 stream quiet quiet stream stream quiet quiet stream`
  - 8 × 120 s + 30 s; it pulls the detached trace + logcat itself at the end.
  - Outputs: `out/ab_u1.pftrace`, `out/steps_u1.txt` (Quest clock), `out/qtx_u1.txt`, `out/logcat_u1.txt`.
- Analysis (Quest clock):
  - `python3 ../quest-latch/ab_link.py out/ab_u1.pftrace out/steps_u1.txt --air-offset-s 0 --guard-s 5 --quest-tx out/qtx_u1.txt`
  - `python3 ../quest-latch/link_audit.py out/ab_u1.pftrace out/steps_u1.txt --air-offset-s 0 --guard-s 5`: must print `TRACE LOSS: none`.
  - `python3 ../quest-latch/link_audit.py --logcat out/logcat_u1.txt --window-ms 2`, then `--window-ms 30`.
- Reading: the table in uplink-t4-analysis §4.
  - **stream > quiet** (post-FEC ~2 % vs ~0.8 %, runs/s ≈ TX/s only in stream) confirms H1: T4 was a capture artefact, and the caveat in link-envelope turns into a correction.
  - **stream ≈ quiet ≈ clean** means T4 needs relaunches, so run U2.

## T6-a: RX ring telemetry, async vs spsc (~10 min)

Question (audit H2 test 4 + test 1): is part of the loss host-side USB ring starvation?

- Air: one `m7b25f46` 17 dBm step of **≥ 580 s**.
- Quest:
  `CAPTURE=detached EXTRA_PREFS='{"rx-diag-ring-ms": 100}' bash pref_ab.sh rxmode rx-diag-mode 120 async spsc spsc async`
  (4 × (120 + 12) + 20 = 548 s; one relaunch per step, the pref is read at link start).
- Analysis: `ab_link.py out/ab_rxmode.pftrace out/steps_rxmode.txt --air-offset-s 0 --guard-s 10`. Read per state
  `dataFEC%`, `usbEmp/s`, `usbDrop/s`, `minArmed`, `cbMax us`, `usbCpl/s`. Also run `link_audit.py` as in U1.
- Reading:
  - `async` with empties > 0 or `minArmed` ≈ 0, and lower `dataFEC%` in `spsc`: host starvation is part of the floor.
  - `minArmed` stays near 8, empties ≈ 0 and `dataFEC%` is equal: the ring is excluded.

## T6-b: CRC pass-through (~7 min)

Question (audit H2 test 2): are the missing frames RF bit errors (the radio saw them, FCS failed) or never demodulated?

- Air: one `m7b25f46` 17 dBm step of **≥ 460 s**.
- Quest:
  `CAPTURE=detached EXTRA_PREFS='{"rx-diag-ring-ms": 100}' bash pref_ab.sh crc rx-diag-keep-corrupted 90 false true true false`
  (4 × 102 + 20 = 428 s).
- Analysis: `ab_link.py` as above. Read `crc/s`, `icv/s` in the `true` steps against the data packets missing per
  second (`dataFEC%` × data rate).
  - `crc/s` covers most of the missing packets: RF bit errors at MCS7.
  - `crc/s` ≈ 0 while 4–6 % is still missing: the frames never reached the MAC (lost in the air or in sync/AGC).
  - In `false` steps the crc counters must read 0 (sanity check).
