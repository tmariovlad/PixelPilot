## Horizon OS quirks (Quest 2)

- **"Controller required" dialog blocks the launch** when the controllers are off. Avoided by declaring
  hand-tracking support in the XR module's manifest (`oculus.software.handtracking`, not required); the Meta hand
  gesture still exits the app [PROVEN: [app/xr/src/main/AndroidManifest.xml](../../app/xr/src/main/AndroidManifest.xml) lines 16-22].
- **The Guardian (boundary) dialog interrupts test sessions**, and the display sleeps when the headset is not
  worn. For bench tests: `adb shell setprop debug.oculus.guardian_pause 1` plus
  `adb shell am broadcast -a com.oculus.vrpowermanager.prox_close`. Restore afterwards with
  `adb shell setprop debug.oculus.guardian_pause 0` and `adb shell am broadcast -a com.oculus.vrpowermanager.automation_disable`.
  The property is lost on reboot. Sources and caveats: [research report 03](research/2026-09-26-quest2/03-system-tweaks-cfw-status.md)
  (Guardian / proximity rows). Rule of thumb for this repo: see [CLAUDE.md](../../CLAUDE.md) (Quest test hygiene).
- **"Launch is blocked because: a Reprojected OS dialog is currently showing"**: a pending USB-permission dialog
  (`com.oculus.os.vrusb/UsbPermissionActivity`) blocks launching immersive apps. Answer or close the dialog in the
  headset, or `adb shell am force-stop com.oculus.os.vrusb` [PROVEN: seen on the device, 2026-09-26].
- **`adb shell cmd wifi connect-network …` on Horizon OS joins a network only if it is already saved.**
  - For a new network it returns without joining [PROVEN: seen on the device, 2026-09-26]: join it once from the headset's own settings.
  - Once saved, `cmd wifi connect-network OpenIPC wpa2 12345678` moved the Quest onto the air unit's AP 3 times out of 3, with no one touching the headset [PROVEN: 2026-09-27, `mWifiInfo SSID: "OpenIPC" … IP: /192.168.0.10`].
  - When the AP goes away the Quest falls back to a saved home network by itself (Zeul36 on 2026-09-27, not the Zeul37 it had before). `cmd wifi list-networks` shows what is saved.
  - Correction 2026-09-27: this line used to say the command is always ignored.
- **Display stuck at 90 Hz**: 120 Hz has to be enabled on Quest 2 under Settings → System → Display; see the
  [smoke checklist](../xr-quest.md#smoke-checklist-first-run-on-a-headset).
- **Picture corruption on a light Wi-Fi test stream**: Quest Wi-Fi power save drops or bunches a light UDP stream;
  keep the radio busy. See [first on-device results](decoder-levers.md#first-on-device-results-quest-2-2026-09-26-horizon-os-build-up1a231005007a1)
  (the `filler()` in [rtp_pace.py](../../scripts/quest-latch/rtp_pace.py) does this).
- **`xr_thread_hints` has no effect**: the runtime rejects every hint with `-1000003001`; see
  [first on-device results](decoder-levers.md#first-on-device-results-quest-2-2026-09-26-horizon-os-build-up1a231005007a1).
- **No `c2.android.*` software decoders** for apps on Horizon OS; see
  [codec, component and resolution](decoder-levers.md#codec-component-and-resolution-2026-09-26).
- **Image upside-down or mirrored**: toggle *XR: flip image vertically* (lever table in the [guide](../xr-quest.md#use)).

## The app, the adapter and the link

- **Release PixelPilot 0.21.0 crashes on launch** (`BackgroundServiceStartNotAllowedException`) if it is started
  while the headset sleeps: see [Build and install](../xr-quest.md#build-and-install). Wake the headset first.
- **Hot-plugging the RTL8812AU crashed the app twice** (devourer EEPROM read exception, then a libusb segfault in
  `~RtlJaguarDevice`); the third enumeration worked. Unplugging the RTL from a running XR app did **not** kill it on 2026-09-27 (pid 15738 survived from 13:12:27 past 13:36, no `am_proc_died`) [PROVEN: logcat events]. The earlier crashes were probably on plug-in / re-enumeration [INFERRED: EEPROM read and device teardown are enumeration-time paths]. Details and the fix still needed: "Known issue seen during this
  work" at the end of [Phase lock](compositor-phase.md#phase-lock-steering-the-source-onto-the-compositor-latch-proof-of-concept-2026-09-26).
- **Plugging the adapter may open the wrong app**: `USB_DEVICE_ATTACHED` can open the `.xr` app's 2D
  `VideoActivity` instead of the release PixelPilot, because both builds declare the same filter on
  `.VideoActivity` [PROVEN: [app/src/main/AndroidManifest.xml](../../app/src/main/AndroidManifest.xml) lines 52-72; the
  debug build only adds `applicationIdSuffix ".xr"`]. Start the XR mode from **Video → Launch XR (Quest)** in the app
  you want.
- **No video from a real OpenIPC air unit** (air unit in APFPV instead of wfb, `drone.key`/`gs.key` pair, link id 0
  vs 7669206): see [First real link](real-link.md#first-real-link-quest-2--rtl8812au--openipc-air-unit-2026-09-26),
  steps 1-3.
- **~96 ms decode on the real stream** (the decoder holds ~16 frames): `dec_picture_order` must be on; see
  [First real link](real-link.md#first-real-link-quest-2--rtl8812au--openipc-air-unit-2026-09-26).
- **Multi-slice H.264 shows as broken frames**: needs *whole access units* (`au_aggregation`) or a single-slice
  encoder; see [codec, component and resolution](decoder-levers.md#codec-component-and-resolution-2026-09-26).
- **The ESP32 + LDR G2G rig reads nothing through the lenses** (the backlight flashes ~1 ms per frame): use a
  photodiode or 480 fps slow motion; see [Measuring](../xr-quest.md#measuring-the-point-of-this-mode).

- **The air unit sends no video after a test, even after a power cycle.** waybeam's destination stays `127.0.0.1` from the wfb switch. Run `linkmode-air.sh apfpv`: see [real-link.md § Restoring the air unit after a test](real-link.md#restoring-the-air-unit-after-a-test-2026-09-27).

## More traps hit on 2026-09-26/27

- **Scripted edits change line endings.** Some files in this repo are CRLF and some LF. A Python rewrite with default newline handling converts a file and turns the whole diff noisy. Read and write with `newline=""` and keep whichever ending the file had.
- **NDK APIs newer than minSdk 26** (e.g. `ATrace_setCounter`, API 29) fail to compile with "is unavailable: introduced in Android 29". Fix used in `app/xr` and `app/videonative` CMake:
  - `target_compile_definitions(... __ANDROID_UNAVAILABLE_SYMBOLS_ARE_WEAK__)`
  - `-Werror=unguarded-availability`
  - wrap every call in `if (__builtin_available(android 29, *))`.
  - Inside that guard, never `return` early past code that must still run.
- **`adb install` from Git Bash needs a Windows path:** `adb install -r "$(cygpath -w app/build/outputs/apk/debug/app-debug.apk)"`. With an MSYS path, adb fails to stat the file.
- **Upstream crash, fixed in this fork:** `WfbngLink` read the key from a hardcoded path and crashed when it was absent. It now uses `Context.getFilesDir()/gs.key`, filled by `GsKeyStore.copyToFiles`.
- **Copying files to the air unit:** it has no sftp-server, so use `pscp -scp`. In batch mode pscp also needs `-hostkey "SHA256:…"`. Read the fingerprint on the air unit with `dropbearkey -y -f /etc/dropbear/dropbear_*_host_key`. Plain HTTP from the PC does not work while the PC's Wi-Fi is on the air unit's AP, because Windows treats that network as public and blocks inbound connections.
- **`linkmode-air.sh wfb` reverts itself to APFPV** when `wfb_tx` injects nothing for 12 s (`AIR_STATE=ERROR:wfb_tx-not-injecting-after-poll-reverted-apfpv`). That usually means waybeam is producing 0 fps; check `/var/lib/misc/waybeam-boot.log` and `/tmp/waybeam-switch.log`.
- **The PC can hold `192.168.0.10` on the air unit's AP.** That address is the air unit's fixed video destination. While the PC's Wi-Fi card is connected there, the HIL GS `.208` cannot take `.10`. Disconnect first: `netsh wlan disconnect interface="Wi-Fi 2"`.
- **Heavy packet loss with a strong SNR = distance or walls, not the app** (2026-09-27).
  - With the air unit in another room: ~83–89 % of wfb packets were lost (1295 received, 6550 missing in 8.6 s), although the received packets showed SNR 31.6 dB. The air unit injected all ~1313 pkt/s with 0 drops.
  - The Quest RTL was also transmitting ~100 pkt/s, most likely keyframe/IDR requests caused by the loss [INFERRED].
  - A first on/off test of `adaptive_link_enabled` seemed to fix it. It was a confound: the headset was moved back near the air unit at the same time.
  - Repeated alternately (on/off/on/off, same position): 835/835/836/835 frames per 10 s, quality 472/576/522/509, Quest TX 0 in every run [PROVEN]. Adaptive link is **not** the cause.
  - **Correction 2026-09-27 (later):** the on/off runs were in XR, which ignored `adaptive_link_enabled` (see [XR ignored the link options](#xr-ignored-the-link-options-until-2026-09-27)), and the Quest sent nothing in any run, so on and off were the same state. This A/B says nothing about adaptive link. The loss-vs-position conclusion rests on the controlled re-check in [real-link.md](real-link.md#diagnosing-a-bad-link-2026-09-27), where Quest TX = 0 was measured directly. Whether the ~50 frames/s the Quest injects when adaptive link does run affect the video is measured separately (slot 3d).
  - Check the physical link first. Compare the air unit's `wlan0 tx_packets` with what the Quest receives (`transport_analyze.py` sequence gaps).
- **XR mode gets no video after starting from the 2D screen** ("USB adapter in use — refusing to open", then `CreateRtlDevice error`). This was the adapter handoff race, fixed in `WfbngLink.cpp` on 2026-09-27; see [real-link.md § Boot defaults](real-link.md#boot-defaults-works-on-the-first-try-after-a-reboot-2026-09-27).

- **ADB to the Quest while it is on the air unit's APFPV AP.** hostapd there has `max_num_sta=1`, so the PC's Wi-Fi cannot join as a second client, and the air unit has no `iptables` for NAT. Use an SSH forward over the air unit's eth0 (dropbear allows local forwards): `python3 scripts/quest/air_tunnel.py`, then `adb connect 127.0.0.1:5595` [PROVEN: 2026-09-27]. A `plink -L` tunnel is blocked by the nested-SSH hook on this PC. Local port 5556 is already taken by the P10 car-modem ADB tunnel.

Fixed: the loss count now unwraps with a signed step and reports reorders separately ([rtp_seq.py](../../scripts/quest-latch/rtp_seq.py), test [test_rtp_seq.py](../../scripts/quest-latch/test_rtp_seq.py)). `ab_segments.py` had the same code and now uses the same function.
- **Decoder stuck at ~78 ms after the air unit changed resolution, cause unknown** (2026-09-27). Once, after waybeam restarted from 1080p90 to 640×480 while PixelPilotXr ran, `Decoding:` averaged 78.7 ms (≈ 16 held frames, like the missing picture-order key in [real-link.md](real-link.md)), `WaitInputBuffer` rose to 6.5 ms, the app lost ~65 RTP packets/s and arrivals lagged up to 0.9 s behind capture [PROVEN: logcat + trace `ab_check640`]. - **`VpnToUdpThread` burns a whole core** (2026-09-27): `top -H` on the Quest shows it at 100 % CPU in every app instance, healthy ones included. Upstream loop in `WfbNgVpnService.java` (the `vpnToUdpThread` `run()`): when `vpnInput.read()` returns 0 it `continue`s with no wait, i.e. a busy loop. It did not cause the decoder stall above (present in the healthy runs too), but it costs power and heat on the headset [PROVEN: `top -H -p <pid>`; code]. Cause: the descriptor from `VpnService.Builder.establish()` is non-blocking by default (AOSP `VpnService.java:878`), and libcore `IoBridge.read` returns 0 on EAGAIN instead of blocking (`IoBridge.java:609-612`), so the loop never sleeps [PROVEN: AOSP source]. **Fixed in code (2026-09-27):** the loop moved to [TunToUdpPump.java](../../app/src/main/java/com/openipc/pixelpilot/TunToUdpPump.java), which waits with `poll(POLLIN, 100 ms)` before every read (stop is still seen within 100 ms); test [TunToUdpPumpTest.java](../../app/src/test/java/com/openipc/pixelpilot/TunToUdpPumpTest.java). **Verified on the Quest (2026-09-27, air unit 1080p90 on wfb, alternating builds that differ only by the fix, N = 2):** `VpnToUdpThread` 97.6 / 97.7 % → 0.2 / 0.3 % of a core, whole app 124 % → 27 %, with decode (2.04–2.07 ms), fps (90–91) and link quality (942–949) unchanged [PROVEN: [data](data/measurements-2026-09-27-quest2-vpn-thread-cpu.csv), `scripts/quest/cpu_ab_run.sh`]. The tunnel behaves the same on both builds: `tun0` TX (kernel → app, the pump's direction) keeps growing with 0 TX drops, so the pump reads; RX stays 0 and a ping to 10.5.0.10 gets no reply on either build, i.e. nothing comes back from the air unit through the tunnel in this setup (not caused by the fix). The fixed build is the one installed.
  - **Stop order (fixed 2026-09-27, verified on the Quest):** stopping the tunnel closed the TUN descriptor while the pump was still in poll/read, so every stop logged `read failed: EBADF` from `TunToUdpPump` [PROVEN: logcat during the replug runs]. `stopTunnel` now asks both threads to stop (running flag + closing the UDP:8000 socket, which is what wakes the other thread's blocking `receive()`), joins them (≤ 300 ms; the pump notices within one 100 ms poll), and only then closes the descriptor ([OrderedShutdown.java](../../app/src/main/java/com/openipc/pixelpilot/OrderedShutdown.java), test [OrderedShutdownTest.java](../../app/src/test/java/com/openipc/pixelpilot/OrderedShutdownTest.java), which fails if the descriptor is closed first). Side effect: the UDP → VPN thread now really exits on stop; before, it stayed blocked in `receive()` with port 8000 bound after every stop.
    Verified with [tunnel_cycle.sh](../../scripts/quest/tunnel_cycle.sh) (build f9d87373 = e3de239, 2 sleep/wake cycles, a live logcat capture of the service's tag): 0 EBADF, 0 late-stop warnings, port 8000 released while asleep (0 sockets) and bound exactly once after wake, `tun0` down/up with the cycle, same process throughout, video 82–86 fps after wake on the balcony link [PROVEN: [output](data/tunnel-cycle-2026-09-27-stop-order.txt)]. The build is installed.
  - **A UDP 8001 socket leaked on every link restart, and the uplink died with it (fixed in code 2026-09-27, not yet on the device).** The app's sockets on 8001 (the native wfb TX input for the tunnel, `WfbngLink.cpp` `args->udp_port = 8001`) went from 4 to 6 over those 2 sleep/wake cycles, one per restart [PROVEN: `/proc/net/udp` by uid 10038]. Cause [PROVEN: code]: `WfbngLink` created one `TxFrame` in its constructor (`WfbngLink.cpp:107`) and reused it for every TX thread; `stop()` sets `shouldStop_` (`TxFrame.cpp:521`) and nothing resets it, so after the first link restart in a process each new `run()` opened a socket on 8001 (`TxFrame.cpp:907-908`), saw the stop flag at the first loop turn (`:620-624`) and returned without closing the socket. Consequence [INFERRED: same code path]: after the first sleep/wake or replug within one app process the Quest's uplink (adaptive link, tunnel) sent nothing until the app was restarted. Fix: a fresh `TxFrame` for every TX thread start (the thread captures its own instance), `shouldStop_` is `std::atomic<bool>`, and `run()` closes its UDP socket on every exit path (RAII guard). Host tests [TxFrame_test.cpp](../../app/wfbngrtl8812/src/main/cpp/tests/TxFrame_test.cpp) over real UDP sockets: `run()` closes its socket when stopped (fails on the previous `TxFrame.cpp`), a fresh instance forwards after a restart, and `stop()` is final for an instance. Device check still to do: count 8001 sockets and devourer TX lines across sleep/wake cycles.
- **Relaunching XR mode over a running instance kills the app with SIGABRT in `stopAudio`** (2026-09-27; fixed, verified on the Quest 2).
  - **Repro:** PixelPilotXr is already running `XrVideoActivity` (here it was left running by an earlier test), then `quest_start_xr` (`am start … XrVideoActivity`) is sent again.
  - **What happens:** the running session goes `XR_SESSION_STATE_SYNCHRONIZED -> STOPPING`, the app logs `RX loop exited` and `stopAudio`, then `Fatal signal 6 (SIGABRT) … tid 31278 (Thread-2)`. No new instance comes up and the headset falls back to Home. A second `quest_start_xr`, with nothing running, starts normally [PROVEN: logcat 2026-09-27 01:58:35; tombstone in `dumpsys dropbox` `SYSTEM_TOMBSTONE_PROTO_WITH_HEADERS` 01:58:35].
  - **Stack (frames seen in logcat):**
    - `#07 AudioDecoder::stopAudio()+56`
    - `#08 VideoPlayer::stop(_JNIEnv*, _jobject*)+204`
    - `#09 Java_com_openipc_videonative_VideoPlayer_nativeStop+44`
    - `… VideoPlayer.stop` ← `VideoPlayer.stopAndRemoveReceiverDecoder`
    - Frames #00–#06 (the abort site) were not captured.
  - **Cause: a second close of the same AAudio stream.**
    - `stopAudio()` closed the stream but left `m_stream` pointing at it, and the destructor closed it again. `AAudioStream_close()` releases the stream, so any later stop or close calls into freed memory [PROVEN: source].
    - The audio is opened once, in the `AudioDecoder` constructor. The 2D `VideoActivity` re-opens it after every stop through `startAudio()` → `initAudio()`, because `isInit` is false by then ([VideoActivity.java:1660-1662](../../app/src/main/java/com/openipc/pixelpilot/VideoActivity.java#L1660-L1662)).
    - `XrVideoActivity` calls `stopAndRemoveReceiverDecoder` on every XR session stop (`INACTIVE`) and `start()` on every `ACTIVE`, but never `startAudio()` ([XrVideoActivity.java:172-189](../../app/src/main/java/com/openipc/pixelpilot/XrVideoActivity.java#L172-L189)). So its second session stop runs `stopAudio()` on the stream the first stop already closed [PROVEN: source].
    - The long-running instance had most likely already been through one stop/start, for example when the display slept [INFERRED: not seen in the log].
    - A null stream is not the cause: AAudio returns `AAUDIO_ERROR_NULL` for `nullptr` and does not abort.
    - The abort site, read later from the crash buffer: `#06 libaaudio AAudioStream_requestStop.cfi` → `__cfi_slowpath` → `__cfi_check_fail` → `#00 abort`. The virtual call on the stream object failed the platform's control-flow-integrity check, as it does when the object was already freed [PROVEN: `logcat -b crash`, 2026-09-27 13:01:37].
  - **Fix (2026-09-27):**
    - `stopAudio()` stops and closes only a non-null stream, then sets `m_stream = nullptr`.
    - The destructor reuses `stopAudio()` instead of closing a second time itself.
    - `AudioDecoder.h` now includes `<cstring>` for the `memcpy` it uses; it compiled on the NDK only through a transitive include.
  - **Test:** [AudioDecoder_test.cpp](../../app/videonative/src/main/cpp/tests/AudioDecoder_test.cpp) runs against a fake AAudio ([host_shim/aaudio/AAudio.h](../../app/videonative/src/main/cpp/tests/host_shim/aaudio/AAudio.h)) that counts every call on a closed stream.
    - Before the fix: 2 of 4 tests failed (second stop, and destructor after stop, each made 2 calls on the closed stream).
    - After the fix: 4 of 4 pass (47 of 47 in the host suite at that commit), and `:app:videonative:assembleDebug` builds [PROVEN: WSL Ubuntu-22.04 ctest, Gradle].
  - **Verified on the Quest 2 (2026-09-27, slot 3c)** with [stop_crash_check.sh](../../scripts/quest/stop_crash_check.sh). Air unit 1080p90 wfb; the link was degraded at the time, so only crash and video start were judged.

  - **Opus decoder freed the wrong way and leaked, fixed too (2026-09-27).**
    - The destructor freed the decoder with `delete`. But opus.h says a decoder from `opus_decoder_create()` is freed with `opus_decoder_destroy()` ([opus.h:509-512](../../app/videonative/src/main/cpp/libs/include/opus.h#L509-L512)) [PROVEN]. libopus allocates it with `malloc` (`opus_alloc`), so `delete` was undefined behaviour [INFERRED: upstream libopus `os_support.h`, not vendored here].

    - Tests `DestructorFreesTheOpusDecoderWithOpusDestroy` and `ReinitDoesNotLeakTheOpusDecoder`: red before the fix (0 destroyed; 3 created, 0 freed after two re-inits), green after. The host suite passes 49 of 49.
- **The wfb tunnel only works on the Quest side; the air unit has no tunnel end** (2026-09-27). With the air unit on wfb (`linkmode-air.sh wfb`), `tun0` on the Quest sends ~10 packets/s and never receives any (RX 0), and a ping to 10.5.0.10 gets no reply, on the old and on the fixed build alike [PROVEN: `/proc/net/dev` on the Quest, see the `VpnToUdpThread` entry above].
  - App side, as in standard wfb-ng [PROVEN: `app/wfbngrtl8812/src/main/cpp/WfbngLink.cpp:94-100,265-277`, `WfbngLink.hpp:25-26`]: air → Quest on radio port 32 (0x20) → UDP 8000 → `WfbNgVpnService` → `tun0` (10.5.0.3/24); Quest → air from `tun0` → UDP 8001 → TX on radio port 160 (0xA0), link id 7669206, FEC 1/5, MCS0, `gs.key`.
  - What uses it: the adaptive-link thread sends its `message …` line every 100 ms to **10.5.0.10:9999** through the tunnel [PROVEN: `WfbngLink.cpp:484-485,568,579`]. That is the ~10 packets/s; with FEC 1/5 the Quest RTL injects ~50 frames/s on the video channel, which matches the ~51 devourer `TX DESC` log lines/s seen on 2026-09-27 [INFERRED].
  - Air side, read-only on `.132` while on wfb [PROVEN: `ps`, `ip addr`, `ls /opt/linkmode /usr/bin`]: only the video `wfb_tx -i 7669206 -p 0` runs. There is **no `wfb_rx` for port 160, no `wfb_tx` for port 32, no `wfb_tun` and no tun interface / 10.5.0.10**; `/opt/linkmode/` ships only `wfb_tx` and `wfb_setfec`, and `/usr/bin` has no `wfb_*` at all. The kernel supports tun (`/dev/net/tun` exists). The only link manager present is `aalink`/`aalink_idr5` (APFPV), which `linkmode-air.sh` stops in wfb mode (`linkmode-air.sh:136`); nothing listens on 9999.
  - **App side, fixed 2026-09-27 (code; to be checked with the air-unit tunnel):** wfb_tun frames each packet as a big-endian u16 length + packet and **aggregates** several per UDP datagram (5 ms by default) or sends empty keep-alives (`wfb-ng/src/wfb_tun.c:51,109,134-160`). The app's downlink stripped one 2-byte header per datagram and wrote the rest to `tun0` as one packet, which breaks as soon as two packets share a datagram; it also left `tun0` at MTU 1500 and read the TUN with a 1024 B buffer (truncating larger packets), while wfb_tun uses MTU 1443 (`wfb_tun.c:37,332`) [PROVEN: code]. Now [TunFraming.java](../../app/src/main/java/com/openipc/pixelpilot/TunFraming.java) is the one home of the framing (encode for the uplink, every packet of a datagram for the downlink, MTU 1443), `tun0` gets MTU 1443 and the pump reads MTU-sized packets; tests [TunFramingTest.java](../../app/src/test/java/com/openipc/pixelpilot/TunFramingTest.java). Until a build with this runs, the air unit's wfb_tun needs `-T 0` (no aggregation).
  - **Cause:** the air unit's wfb mode was built for video only. For the tunnel to work both ways, the air unit needs (1) `wfb_rx -p 160 -i 7669206` with `drone.key` and (2) `wfb_tx -p 32 -i 7669206`, both joined to a tun interface at 10.5.0.10/24 by `wfb_tun` (the binaries are not on the air unit; they come from the same wfb-ng build as its `wfb_tx`), and (3) something on 10.5.0.10:9999 that understands PixelPilot's adaptive-link `message` lines (e.g. OpenIPC's `alink_drone`) if adaptive link is wanted. Nothing else is missing in the app, apart from the framing below. Until then, adaptive link on the Quest only costs airtime on the video channel; turning it off (`adaptive_link_enabled`) stops those ~50 frames/s [PROVEN in XR since the LinkOptions fix; on the balcony link that traffic had no measurable effect on loss or latency, see [slot 3d](#does-the-quests-uplink-hurt-the-video-slot-3d-2026-09-27)].

## Crash when the RTL is plugged in with the display off (fixed in code 2026-09-27)

- **Seen** (reported by the [8d] session from logcat, 2026-09-27 13:58–13:59): with the Quest's display off, plugging the RTL8812AU back in killed the app. The 2D `VideoActivity` died in `onCreate` → `startVpnService` (`VideoActivity.java:361/1390`), then `XrVideoActivity` twice in `onResume` → `WfbServiceControl.startVpn` with `BackgroundServiceStartNotAllowedException`. The release PixelPilot 0.21.0 starts the service the same way.
- **Cause** [PROVEN: AOSP android14-release source; the device is Horizon OS UP1A = Android 14]: `startService()` goes through `ActiveServices.startServiceLocked`, which refuses a start unless `ActivityManagerService.getAppStartModeLOSP` says NORMAL (`ActiveServices.java:940-969`). That refuses whenever the app's **uid is idle** and it is not a pending-top launch (`ActivityManagerService.java:6058-6067`). `ContextImpl` then throws `ServiceStartNotAllowedException`, here `BackgroundServiceStartNotAllowedException` (`ContextImpl.java:1944-1946`). With the display off, an activity started by the USB attach runs in a sleeping, background process state, so the uid stays idle [PROVEN: the three `am_crash` lines read by the [8d] session, e.g. `BackgroundServiceStartNotAllowedException, Not allowed to start service Intent { cmp=com.openipc.pixelpilot.xr/com.openipc.pixelpilot.WfbNgVpnService }: app is in background uid UidRecord{… u0a38 TPSL bg:+33m20s670ms idle …}`, thrown at `ContextImpl.java:1945`; TPSL = PROCESS_STATE_TOP_SLEEPING, the top activity with the display off, and the uid is idle].
- **Fix:** the activities no longer start the service; they **bind** to it. `WfbServiceControl.Binding` binds in `onResume` and unbinds in `onPause`; `WfbNgVpnService.onBind` starts the tunnel for the action `ACTION_BIND_TUNNEL`, `onUnbind` stops it. `bindServiceLocked` has no idle-uid check (`ActiveServices.java:3509` onward), and the app may bind to its own service although it requires `BIND_VPN_SERVICE`, because the owning uid has blanket access (`ActivityManager.java:4681-4683`). The tunnel now lives exactly while an activity is bound, so leaving XR no longer stops the 2D activity's tunnel. No exception is caught or hidden.
  - **The system's own binding is untouched:** `onBind` answers only `ACTION_BIND_TUNNEL`; every other intent, i.e. the system's `VpnService.SERVICE_INTERFACE`, still goes to `super.onBind` (`VpnService.java:420-424`).
  - **Pause and wake:** the activities unbind in `onPause` (headset asleep or taken off), which stops the tunnel, as `STOP_SERVICE` did before. Video does not use the tunnel (it arrives on UDP 5600 from the wfb aggregator), so only the uplink stops. `establish()` makes the system bind too (`Vpn.java:1852,1896`), so the service can outlive our unbind; `onUnbind` therefore returns true, and on the next bind (`onResume` after wake) Android calls `onRebind`, which restarts the tunnel. With `false`, Android would hand back the cached binder without any callback and the tunnel would stay down (`Service.java:583-593`).
  - **VPN permission:** unchanged. `Binding.bind` calls `VpnService.prepare()` first; the 2D activity asks for consent (`onActivityResult` → bind), XR only shows "VPN not granted - start PixelPilot in 2D once".
- **Test:** [VpnStartRuleTest.java](../../app/src/test/java/com/openipc/pixelpilot/VpnStartRuleTest.java) fails if production code calls `startService`/`startForegroundService` again (checked: it fails on the previous `WfbServiceControl`), if `onBind` stops passing other intents to `super.onBind`, or if `onUnbind`/`onRebind` stop asking for and doing the restart. The framework behaviour itself needs the device: replug the RTL with the display off, N ≥ 2, before and after the fix.
- **Verified on the Quest (2026-09-27, 15:00–15:57, headset asleep on the table via `KEYCODE_SLEEP`, the user unplugged and replugged the RTL, alternating builds):** without the fix (428fa1a1) both replugs crashed (`am_crash … BackgroundServiceStartNotAllowedException` right after the `USB_DEVICE_ATTACHED` activity; 2 and 1 crashes) and the app was gone after waking; with the fix (943c6168 = cae687c) both replugs gave 0 crashes, and after waking the video came back (90 fps / decoding) and `tun0` came back with traffic, i.e. the tunnel restarted through `onRebind`. `dumpsys activity services` showed both bindings side by side: ours (`BIND_TUNNEL`) and the system's (`android.net.VpnService`) [PROVEN: [data](data/replug-2026-09-27-display-off.csv), [replug_check.sh](../../scripts/quest/replug_check.sh)]. The fixed build is the one installed.
